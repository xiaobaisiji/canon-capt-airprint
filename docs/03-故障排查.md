## 6. 故障排查手册（按现象查）

### 6.1 快速定位顺序

```
① 作业有没有进 CUPS？   lpstat -o LBP7010C
     没有 → 客户端/网络问题（IPP 403、Windows 客户端、mDNS）
② 进了但不动？          lpstat -p LBP7010C 看状态
③ ccpd 正常吗？         pgrep -a ccpd；ss -ltn | grep 59687
④ 助手在吗？            pgrep -a captmoncnacb
⑤ 助手崩溃了吗？        dmesg | grep -i captmon
⑥ 转换层卡住？          ps -eo pid,user,args | grep -E 'pstocapt3|gs -r600'
⑦ USB 通吗？            sudo /usr/local/sbin/canon-usbreset
```

### 6.2 症状对照表

| 现象 | 根因 | 修复 |
|---|---|---|
| `ccpd` 反复重启，`restart counter` 一直涨 | 单元写成 `Type=simple` | 改 `Type=forking` |
| 日志 `bidiNew() Error! name=/usr/bin/captmoncnacb` | 32 位助手缺库（`exited with 127`） | 装 `libxml2:i386`、`libpopt0:i386` |
| `dmesg` 出现 `captmoncnacb ... segfault at 0 ... f3 a6` | 服务无 locale，msgtable 查不到 → `strcmp(NULL)` | ccpd 单元加 `LANG=en_US.UTF-8` |
| `ccp send_data error, exit` | 后端拿不到数据 / ccpd 回 BUSY | 见 6.3 |
| `ccp recv_packet error, exit` | ccpd 回包异常（多半助手已崩） | 同 6.3 |
| `gs` 与 `captmoncnacb` 同时 `S` 状态不动 | USB 端点 stall，`ccpd` 等打印机响应 | USB 复位 → 断电重启打印机 |
| HTTP 631 返回 **403**（Unix socket 却 200） | `<Location>` 的 `Allow @LOCAL/localhost` 未匹配 | 改 `Allow all` + `ServerAlias *` |
| iOS 打印面板看不到打印机 | TXT 字段不被接受 | 用 4.8 的字段组合 |
| iOS 只有 Letter/Legal | `ReadyPaperSizes` 走了美制分支 | `ReadyPaperSizes A4,A5,B5,Legal`（**不加引号**） |
| A5/B5 出现但 A4 不出现 | `ReadyPaperSizes "A4,A5,B5"` 引号被当字面量 | 去掉引号 |
| 加了 A6 后所有作业卡死 | 手工改 PPD 破坏驱动解析 | 回滚 PPD，不要动 PPD |
| 打印完一张后第二张必卡 | 残留助手占设备 | 单元加 `ExecStartPre=pkill -9 -x captmoncnacb` |
| `ppd` 里 `dmesg` 偶见 `c3pldrv segfault` | 2017 年 64 位构建的已知缺陷 | 不影响出纸，忽略 |

### 6.3 卡死急救三步（最高频）

```bash
sudo pkill -9 -x captmoncnacb          # 清掉占用设备的残留助手
sudo /usr/local/sbin/canon-usbreset    # 复位 USB，清 stalled 端点
sudo systemctl restart ccpd            # 重启守护进程
```

三步无效 → **拔打印机电源 15 秒再插回**（软件复位救不了半死的固件），然后：

```bash
sudo systemctl restart ccpd
lp -d LBP7010C -o media=A4 /usr/share/cups/data/default-testpage.pdf
```

### 6.4 逐条详解

**① `Type=simple` 导致进程被杀**

```
# systemctl status ccpd
   Active: activating (auto-restart)
  Process: 1893394 ExecStart=/usr/sbin/ccpd (code=exited, status=0/SUCCESS)
  Main PID: 1893394 (code=exited, status=0/SUCCESS)
# journalctl -u ccpd
  ccpd.service: Scheduled restart job, restart counter is at 398.
  ccpd.service: Deactivated successfully.
```

`ccpd` fork 后父进程退出，systemd 判定服务结束并杀掉 cgroup。改 `Type=forking` 即可，观察点：`Main PID: ... (ccpd)` 且有两个 ccpd 进程。

**② 32 位助手缺库**

```
ccpd: DA[0]: bidiNew() Error! name=/usr/bin/captmoncnacb
```

```
$ file /usr/bin/captmoncnacb
ELF 32-bit LSB executable
$ ldd /usr/bin/captmoncnacb | grep 'not found'
libxml2.so.2 => not found
libpopt.so.0 => not found
```

装 `libxml2:i386 libpopt0:i386` 后必须 `ldconfig`，否则 32 位加载器仍找不到（Canon 的二进制按老式路径 `/usr/lib` 查找，必要时补一条 `ld.so.conf.d`）。

**③ locale 导致 segfault（最隐蔽）**

```
captmoncnacb[1935657]: segfault at 0 ip 000000000804be4b error 4 in captmoncnacb[3e4b,...]
Code: ... fc 8d bb 4d f9 fd ff <f3> a6 ...
```

`f3 a6` = `repz cmpsb` = `strcmp`。根因是

```xml
<PswMsgTable>
 <MsgList locale="en">   <!-- 只有 en -->
```

服务环境无 `LANG` → 查不到条目 → NULL → 崩。加 `Environment=LANG=en_US.UTF-8`。

**④ CUPS 返回 403**

```
$ curl -H 'Host: <NAS-IP>:631' http://<NAS-IP>:631/printers/LBP7010C
403
$ curl --unix-socket /run/cups/cups.sock http://localhost/          # 200
```

说明 TCP 连接的 ACL 匹配失败。把每个 `<Location>` 改成 `Order allow,deny` + `Allow all`，并加 `ServerAlias *`。

**⑤ 纸张列表只有 Letter/Legal**

iOS 的纸张列表来自 IPP 的 `media-ready`，而 CUPS 的默认值是按地区二选一（源码 `scheduler/conf.c`）：

```c
if (!ReadyPaperSizes)
  ReadyPaperSizes = 美制 ? "Letter,Legal,Tabloid,4x6,Env10" : "A4,A3,A5,A6,EnvDL";
```

显式声明即可：

```conf
DefaultPaperSize A4
ReadyPaperSizes A4,A5,B5,Legal
```

**绝对不要给这个值加引号**——CUPS 不做 shell 式去引号，`"A4,A5,B5"` 会被切成 `"A4` / `A5` / `B5"`，结果是“只有 A5 生效”这种诡异现象。

**⑥ 不要手工往 PPD 里加尺寸**

为让 A6 出现，往 PPD 里插了 `*PageSize A6` / `*PageRegion A6` / `*PaperDimension A6` / `*ImageableArea A6` 四条后，`cupstestppd` 只报 WARN，但随后**所有**作业都卡在

```
gs -r600 -sDEVICE=opvp -sDriver=libcanonc3pl.so -sModel=LBP7010C ...
```

`gs` 与 `captmoncnacb` 同时进入 `S` 状态，手机也不能打了。回滚 PPD 立即恢复。设备物理上没有 A6 纸路，不值得为它冒险。

## 6.5 手机打印专属问题（PC 正常、手机异常）

### 现象 A：手机打 PDF 表头出现**黑块**，电脑打印正常

**根因**：CAPT 驱动对 **CMYK 图像**渲染不可靠。

这个 PDF 是印刷用的（Illustrator 导出，101 张 CMYK JPEG），而 CAPT 的 opvp 驱动是给消费级彩激设计的（`CNOutputDepth=1`），处理 CMYK 时会算错，深色区域直接被压成 100% 黑。

电脑正常，是因为 **Windows 的 PS 驱动在本地就把 CMYK 转成 RGB 位图**了，NAS 收到的已经是干净的 PS。

**判定方法**：

```bash
cupsfilter -i application/pdf -m application/vnd.cups-postscript your.pdf > /tmp/x.ps
grep -c 'DeviceCMYK' /tmp/x.ps    # 数值几十上百就是它
```

**修复**：在转 PS 之前先把颜色空间转成 RGB：

```sh
gs -q -dBATCH -dNOPAUSE -dSAFER -sDEVICE=pdfwrite -dCompatibilityLevel=1.7 \
   -sColorConversionStrategy=RGB -dProcessColorModel=/DeviceRGB \
   -sOutputFile=- input.pdf
```

仓库里的 `scripts/canon-pdf-filter.sh` 就是做这件事，并且**只在检测到 `/DeviceCMYK` 时才转换**，纯 RGB 文件直接透传。

### 现象 B：手机打印比电脑慢很多（十几秒机器才动）

**根因**：**渲染在哪台机器上做**。

| 谁打印 | 发到 NAS 的是什么 | NAS 要做什么 | 耗时 |
|---|---|---|---|
| 电脑（PS 驱动） | 已渲染好的 **PostScript** | 只转发 | ~2 秒 |
| 手机 | **原始 PDF / 照片** | 解码 + 转 RGB + 栅格化 + 打包 CAPT | 10~15 秒 |

电脑把渲染工作放在了**电脑的 CPU**（强）上；手机只能把原始文件丢过来，渲染全压在 **NAS 的 CPU**（弱）上。

**实测数据**（A4 / 600dpi）：

| 内容 | CAPT 数据量 | 驱动渲染 | 端到端 |
|---|---|---|---|
| 6MB 手机照片 | 14 MB | ~9 s | ~12 s |
| 印刷用 CMYK PDF | 4.7 MB | 2.6 s + 转换 9 s | ~15 s |
| 纯文本 | 极小 | <1 s | ~0.5 s |

**本仓库已包含的优化**：

1. **照片直通**：`jpeg2pdf` 把 JPEG 原样嵌进 PDF，不重编码。相比 CUPS 自带的 `imagetopdf`（放大到 600dpi、存成 30MB+），快 **20 倍**
2. **PDF 按需转换**：纯 RGB 的 PDF 直接透传，省掉一次完整 gs 重编码
3. **转换缓存**（可选）：同一份 PDF 反复打印时可缓存转换结果

**做不到的**：600dpi 下 A4 一页是 3500 万像素，NAS 单线程栅格化就要 8~9 秒。要更快只有两条路：

- 降到 400dpi / 300dpi（数据量和耗时按平方下降，画质受损）
- **换更强的主机**（N100 小主机，栅格化快 2~3 倍，可到 6 秒左右）

### 现象 C：A5 / Legal 要按一下进纸键，A4 不用

**不是软件问题**。纸盒里装的是 A4，作业要 A5/Legal 时尺寸不匹配，打印机会停下来等确认；按进纸键等于「就用纸盒里的纸强行打」。

**解决**：换纸，并在 Windows 的佳能驱动「设备设置 → 纸张来源」里把纸盒尺寸改成 A5；或打印时明确指定「多用途托盘」。
